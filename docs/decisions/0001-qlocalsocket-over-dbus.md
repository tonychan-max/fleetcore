# 0001. 端末内部のプロセス間通信に QLocalSocket を使う

## 状態

採用 — 2026-08

## 背景

Phase 2 で端末側を複数プロセスに分割する（受信 / 交換機 / 画面）。
同一マシン内・同一ユーザ配下のプロセス間で、電文を双方向にやり取りする手段が必要。

制約：

- Linux が主対象だが、**Windows でも同じコードが動くことが望ましい**（実務環境が Windows のため、比較検証に使いたい）
- 組込み・車載相当の環境を想定する。常駐デーモンを増やしたくない
- 依存ライブラリは可能な限り増やさない

## 選択肢

1. **D-Bus** — Linux デスクトップの事実上の標準。KDE Connect が採用している
2. **QLocalSocket** — Qt 標準。Unix domain socket / named pipe を抽象化
3. **生の Unix domain socket** — 依存ゼロ
4. **System V メッセージキュー**（サーバ側と同じ方式）

早期に外したもの：

- **TCP over loopback** — 同一マシン内でポート番号を消費する理由が無い。ファイアウォールの影響も受ける
- **共有メモリのみ** — 通知機構が無い（§3-4）。ポーリングになる

## 決定

**QLocalSocket。**

## 理由

- **依存が Qt だけで完結する。** GUI に Qt を使う以上、追加依存がゼロ
- **同じコードが Linux / Windows 両方で動く。** Linux では Unix domain socket、Windows では named pipe に自動で切り替わる
- D-Bus は `dbus-daemon` の常駐が前提。組込み想定では重い
- 生の Unix domain socket は Windows で動かない。抽象化を自分で書くことになり、それは QLocalSocket の再実装

サーバ側で System V メッセージキューを使っているのに端末側で使わないのは、
**端末側は Qt のイベントループの中に居るため**。`QLocalSocket` はシグナル/スロットで
イベントループに自然に乗るが、System V メッセージキューは別スレッドか自前ポーリングが要る。

## 代償

- **D-Bus が持つ内省ツール（`QDBusViewer` 等）が使えない。**
  D-Bus ならインタフェースを外部から覗ける。QLocalSocket は生のバイト列なので何も見えない
  → **対策**：`term_router`（Step 9）に電文トレースログを実装する。これは代償に対する義務であり、任意機能ではない
- **サービス発見の仕組みが無い。** 接続先のソケットパスを設定で持つ必要がある
  → `config/fleetcore.toml` に記載し、`docs/CONFIG.md` に台帳登録する
- **メッセージ境界が無い。** バイトストリームなので、受信側でヘッダの `length` を見た分割処理が必要
  → 共通ヘッダに `length` があるため実装可能。むしろ `length` の必要性を裏付ける

## 検証方法

- Phase 2 完了時点で、Windows 上で同一ソースがビルド・動作するか確認する。動かなければこの判断の主要な理由が消える
- トレースログだけでデバッグが成立するか。成立しないなら D-Bus の内省ツールの価値を過小評価していたことになる
