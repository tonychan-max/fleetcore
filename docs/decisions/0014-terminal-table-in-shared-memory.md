# 0014. 端末テーブルを共有メモリに置き、テーブル全体を1つのセマフォで保護する

## 状態

採用 — 2026-10（Step 3 で実装）

## 背景

Step 2〜6 の間、`locator` は端末番号からプロセス索引への対応を
コード内のハードコード表で持っていた。

```cpp
constexpr TermMapping TABLE[] = {
    { "1001", IDX_TERMD_BASE + 1 },
    { "1002", IDX_TERMD_BASE + 2 },
};
```

これには2つの問題がある。

- **どの端末が存在するかが、システムではなく起動した人の手に委ねられている**
- **対応関係しか持たず、状態が無い。** 端末が今接続しているかどうかを誰も知らない

ARCHITECTURE §3-4 は「共有メモリ = snapshot、メッセージ = delta」と定めている。
Step 2 で delta（メッセージキュー）は実装したが、snapshot は未実装だった。
この ADR はその残り半分を埋める。

## 判断1：テーブルの所有と生成

### 選択肢

1. **先に起動したプロセスが作る**（`IPC_CREAT`、`IPC_EXCL` なし）
2. `locator` が作る
3. 初期化専用のプロセスを置く

### 決定

**案1。** どのプロセスが先に起動しても動く。

カーネルが新規セグメントをゼロで埋めるため、全行が
`term_no == 0`（空き）・`state == TERM_STATE_UNUSED` で始まる。
**明示的な初期化は不要であり、これは偶然ではない。** 0 を「空き」に割り当てたのはこのため。

### 端末はプロセス起動時に登録する

`termd` は起動した時点で自分の行を登録する。端末が一度も接続していなくても行は存在する。

**これは一車一プロセスの設計（ARCHITECTURE §2）と対になっている。**
プロセス数は「今接続している台数」ではなく「登録されている台数」で決まる。
トンネル内の車両にも `termd` が存在し、行が存在するので、
`locator` は指令の宛先を解決できる。保持して後で送るかどうかは
`termd` の判断であり、`locator` の責務ではない（Phase 4）。

## 判断2：セマフォの数

### 選択肢

1. **テーブル全体で1つ**
2. 行ごとに1つ（64個）
3. 行をグループ分けしてグループごとに1つ

### 決定

**案1。**

### 理由

- **書き込み同士は衝突しない。** 各 `termd` は自分の行しか書かない。
  競合は「`termd` が書いている間に `locator` が読む」だけである
- **書き込みは稀で、短い。** 接続・切断時のみ、臨界区間はマイクロ秒単位。
  64行の全走査でも数マイクロ秒
- **細粒度ロックはデッドロックを持ち込む。** これが最大の理由。
  `snapshot()` は全行を読むため、行ごとにロックがあると全ロックの取得が必要になる。
  別の操作が異なる順序でロックを取れば、特定のタイミングでのみデッドロックする。
  **再現困難なバグの典型であり、得られる並行性はこの規模では測定できない**

**一車一プロセスだからといって、一車一セマフォにはならない。**
プロセス数は隔離の要求で決まり、ロック数は競合の形で決まる。両者は独立している。

### 検討したが採らなかった代替：共有メモリ上の robust mutex

`pthread_mutex` を `PTHREAD_PROCESS_SHARED` と `PTHREAD_MUTEX_ROBUST` 付きで
共有メモリに置く方法がある。

| | System V + `SEM_UNDO` | robust mutex |
|---|---|---|
| ロック保持者が kill された | カーネルが**黙って**ロックを返す | 次の取得者が `EOWNERDEAD` を受け取る |
| 異常を知れるか | **知れない** | **知れる**。書きかけの行を検査できる |

**技術的には robust mutex の方が優れている。** 異常終了を隠さず通知するため。

今回採らなかったのは、ARCHITECTURE §6 が System V を定めており、
実務の構成とも一致するため。**Phase 5 で端末数を増やす段階で再検討する。**

## 判断3：`SEM_UNDO`

### 決定

**`lock()` / `unlock()` には付ける。初期化の `+1` には付けない。**

### 理由

`SEM_UNDO` は「このプロセスが終了したら、行った調整をカーネルが逆に戻す」という意味。

- **ロックの取得に付けない場合**：ロック保持中に `kill -9` されると値が 0 のまま残り、
  **全プロセスが永久に待つ**。書きかけの1行よりはるかに深刻
- **初期化の +1 に付けた場合**：作成者が終了した時点で +1 が取り消され、値が 0 に戻る。
  **作成者が正常終了しただけでシステム全体が止まる**

ロック取得は「借りる」操作であり、死んだら返すべき。
初期化は「初期状態を設定する」操作であり、設定した者がいなくなっても残るべき。
**同じ `semop` でも意味が違う。**

### 代償

`SEM_UNDO` が黙ってロックを返すため、**書きかけの行が残っても誰も気づかない。**
臨界区間が数命令なので窓は狭いが、ゼロではない。上記 robust mutex の比較を参照。

## 判断4：セマフォ初期化の競合

System V セマフォは**生成と初期値設定が原子的でない。**
2つのプロセスが同時に起動すると、片方が初期化を終える前にもう片方が使い始めうる。

### 決定

1. `IPC_CREAT | IPC_EXCL` で「自分が作った」か「既にあった」かを区別する
2. 作った側が `semop(+1)` で初期値を設定する
3. 既にあった側は `sem_otime` が非ゼロになるまで待つ。
   **規定回数待っても非ゼロにならなければ、エラーとして起動を中止する**

### 実装中に見つかった誤り

当初は作成者が `semctl(SETVAL)` で初期化していた。
**`SETVAL` は値を変えるが `sem_otime` を更新しない。** `sem_otime` を更新するのは `semop` だけ。

その結果：

- 後から起動したプロセスは、誰かが最初に `lock()` するまで毎回 1 秒待たされていた
- 待ち切った後、**エラーを出さずに `true` を返して処理を続けていた**

単一プロセスのテストでは現れない。**2つのプロセスが特定の順序で起動したときだけ**現れる。
コードレビューで発見した。

### 残る窓

作成者が `semget` 成功後、`semop(+1)` の前に kill されると、
セマフォは値 0・`sem_otime` 0 のまま残る。後続プロセスは今はエラーで止まるが、
**セマフォ自体は残り続け、次回起動時も同じ状態になる。** `ipcrm -s` で手動除去が必要。
Step 7 でメッセージキューの残留と合わせて扱う。

## 判断5：読み出しはコピーで返す

```cpp
bool find(uint32_t term_no, TermEntry& out) const;   // 採用
const TermEntry* find(uint32_t term_no) const;       // 不採用
```

ポインタを返すと、呼び出し側がそれを保持している間に別のプロセスがその行を書き換えうる。
**コピーはロック保持中に行われるので、得られるのは一貫したスナップショット。**

共有メモリを扱うコードで最も誤りやすい箇所。

## 判断6：`TermEntry` にもレイアウト検証を付ける

```cpp
#pragma pack(push, 1)
struct TermEntry { ... };
#pragma pack(pop)
static_assert(sizeof(TermEntry) == 20, ...);
```

ARCHITECTURE §5 の元の定義には `pack` も `static_assert` も無かった。

**共有メモリも契約である。** 別々にコンパイルされたプロセスが同じメモリを見る以上、
レイアウトは1バイトも違えてはならない。電文と同じ問題であり、同じ保護を受けるべき。
`layout_dump` にも追加し、CI の GCC / Clang 比較の対象に入れた。

### 実装中に見つかった誤り

当初 `sizeof(TermEntry) == 24` と書いた。正しくは 20。
**`layout_dump` で実測し、手計算と照合する手順（ADR-0003）を飛ばした結果である。**
`static_assert` がコンパイル時に `20 == 24` で止めた。

### 未整列の `last_seen`

`last_seen`（`uint64_t`）はオフセット 12 にあり、8 の倍数ではない。
ARM でポインタ経由で直接読むと問題になりうる。

**`find()` がコピーで返すため、現状は安全。** ADR-0008 で
`reinterpret_cast` を避けたのと同じ理由である。
`reserved` を 7 バイトにして全長 24・オフセット 16 にすれば整列するが、
使わない性質のために 4 バイト増やす理由は今のところ無い。

## 代償

- **`state` は「TCP 接続が存在するか」しか表さない。**
  トンネル進入・電源断・ケーブル抜けでは、相手が切断を通知できないため
  **半開接続**になり、`state == CONNECTED` のまま残る。
  TCP keepalive の既定は Linux で 2 時間であり、実用にならない
  → Phase 5 の位置報告で `touch()` を呼び、`last_seen` の更新が途絶えたら離線と判定する。
    **位置報告そのものがハートビートを兼ねる**ため、別のハートビート電文は不要
- **端末番号とスロットの対応がコードに埋まっている**（スロット n → 端末番号 1000+n）
  → 本来は設定から来るべき
- **capabilities がハードコード**（接続時に `CAP_LOCK` 固定）。
  ARCHITECTURE §5 は端末自身が接続時に申告すると定めているが、
  それにはハンドシェイク電文が必要
- **`maint_gui` の端末選択は依然ハードコード。**
  保守端末が共有メモリを直接読むのは誤りである（クライアントであり、別マシンにありうる）。
  端末一覧電文が必要で、Phase 3 のコード生成の題材にする
- **共有メモリとセマフォは誰も削除しない。** 全プロセス終了後も残る。Step 7

## 検証方法

実施済み：

- `termd 1` と `termd 2` を起動し、`ipcs -m` で `nattch = 2`、`bytes = 1280`（64 × 20）
- 全プロセスで往復が従来と同じく成立すること
- **未登録端末への指令が `MESSAGE` 等級で拒否されること。**
  従来は `locator` が宛先を解決した上で `send_to` が失敗し `PEER` 等級だった。
  等級が変わったこと自体が、テーブルが参照されている証拠
- ロック保持者を `kill -9` した後、`ipcs -s -i` で `semval` が 1 に戻っていること

今後：

- **Phase 5 で端末数を増やし、ロック待ちが測定可能になるか。**
  なるなら細粒度化ではなく、まず robust mutex への移行と読み取り頻度の削減を検討する
- 半開接続の検出が `last_seen` で機能するか
