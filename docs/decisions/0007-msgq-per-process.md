# 0007. System V メッセージキューをプロセスごとに1本持つ

## 状態

採用 — 2026-08（Step 2 で実装）

## 背景

Step 2 で `gateway` → `locator` → `termd` の3プロセスを繋ぐ。
プロセス間の delta 伝達には System V メッセージキューを使う（ARCHITECTURE §6）。

`termd` は端末ごとに1プロセス存在するため、キューの割り当て方は端末数に直結する。

## 選択肢

1. **プロセスごとに1本。キーは `MSGQ_KEY_BASE + プロセス索引`**
2. 全体で1本。`mtype` に宛先プロセス索引を入れて区別する
3. 経路ごとに1本（gateway→locator 用、locator→termd 用）

早期に外したもの：

- **Unix domain socket** — 端末側は ADR-0001 で QLocalSocket を選んだが、
  サーバ側はイベントループを持たない。受信でブロックする方が単純

## 決定

**プロセスごとに1本。キーは `MSGQ_KEY_BASE + プロセス索引`。**

gateway 0x46431000 + 1000
locator 0x46431000 + 2000
termd n 0x46431000 + 3000 + n

自プロセスのキューは `IPC_CREAT` で作成し、他プロセスのキューには接続のみ行う。

## 理由

- **`ipcs -q` の出力とプロセスが1対1で対応する。**
  障害時にどのキューが誰のものか、キー値を見るだけで分かる
- ARCHITECTURE §2「プロセス索引に ID を埋め込む」の延長。索引が分かればキューが分かる
- **案2（全体で1本）は、1つのキューが溢れると全プロセスが巻き込まれる。**
  ある端末への送信が詰まったせいで別の端末への指令が届かない事故が起きうる
- 案3（経路ごと）は `termd` が N 個ある時点で結局 mtype による多重化になり、案2と同じ問題を持つ

## 代償

- **起動順序に制約がある。** 受信側のキューが存在しないと送信できないため、
  データフローとは逆順（`termd` → `locator` → `gateway`）で起動する必要がある
  → 現状は手動。本来は次のいずれかで解決すべき
    - 送信失敗時に保持して再送する（Phase 4 の store-and-forward）
    - 起動時に依存プロセスの存在を確認する
    - supervisor に依存順序を宣言する（Step 7 の systemd）
- **依存不足が起動時に検出されない。** Step 2 の実装では `gateway` は自キューだけ作り、
  `locator` のキューは送信時に初めて開く。したがって `locator` が居なくても `gateway` は起動し、
  **最初の電文で初めて失敗が分かる**
  → Phase 4 で保持できるようになれば、これは欠点ではなく利点になる
- **キュー数が端末数に比例して増える。**
  System V には system-wide の上限がある（`/proc/sys/kernel/msgmni`）
  → Phase 5 で 50 台模擬する際に実測する。上限に当たるなら案2への変更を検討
- **プロセスが異常終了するとキューが残る。**
  次回起動時に古いキューを掴み、前回の未読メッセージを読む可能性がある
  → Step 7 で signal ハンドラを入れる際に対処。それまでは `ipcs -q` / `ipcrm -Q` で手動確認
- **System V メッセージキューにはタイムアウト機能が無い。**
  終了フラグを確認するために、`IPC_NOWAIT` と短いスリープによるポーリングで代用している
  （`mq_recv_timeout_ms`、既定 200ms）。50ms ごとに起きるため無駄がある
  → **要検討**：POSIX メッセージキュー（`mq_timedreceive`）なら原生でタイムアウトを持つ。
    ただし ARCHITECTURE §6 の記述と実務の構成から離れるため、Step 2 では採用しない
- `locator` が送信のたびにキューを open している。1メッセージごとの `msgget` は無駄
  → Step 3 で端末テーブルを共有メモリ化する際、キューハンドルもキャッシュする

## 検証方法

- **Phase 5：50台の `termd` を同時起動し、`ipcs -q` が破綻しないか確認する。**
  破綻するならこの判断は端末数に対してスケールしない
- **1つの `termd` を kill したとき、他の端末への指令が影響を受けないこと。**
  受けるなら「プロセスごとに1本」の利点が出ていない
- ポーリング方式の CPU 使用率を測る。無視できない水準なら POSIX キューへの移行を検討する
