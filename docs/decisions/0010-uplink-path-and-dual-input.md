# 0010. 上り電文は locator を経由せず、gateway が直接受け取る

## 状態

採用 — 2026-08（Step 3 で実装）

## 背景

Step 3 で上り方向（ロック完了通知）を追加した。
下りは `gateway → locator → termd` の3段だが、上りの経路を決める必要がある。

同時に、`gateway` は標準入力と自プロセスのキューという**2つの入力源**を
同時に見る必要が生じた。これも本 ADR で扱う。

## 判断1：上りの経路

### 選択肢

1. **`termd` → `gateway` を直接繋ぐ**
2. `termd` → `locator` → `gateway` と、下りと対称にする

### 決定

**案1。上りは locator を経由しない。**

### 理由

- ARCHITECTURE §3-2 の三動作は**解析 → 解決 → 変換**。
  上りに「解決」は要らない。`termd` は宛先（`gateway`）を既に知っている
- 対称性のために1段挟むのは形式主義であり、遅延とキュー1本分の資源を無駄にする
- **上下で経路が違うこと自体が §3-6 の裏付けになる。**
  上りと下りは「向きが逆の同じもの」ではなく、性質が違う

### 代償

- **図が非対称になり、初見で説明が要る。**
  → ARCHITECTURE §2 の構成図に上り経路を明記する
- 将来、上りにも「宛先の解決」が必要になる可能性がある。
  複数の保守端末が接続し、指令を出した端末にだけ応答を返す場合など
  → その時点で `gateway` 内部に解決を持つか、`locator` を経由させるかを再検討する。
    **現時点で必要のない汎用性を先に作らない**

## 判断2：gateway が2つの入力源を扱う方法

### 背景（実装中に判明した問題）

上りを実装した直後、**上り電文が一切処理されないという現象が起きた。**

`ipcs -q` で確認したところ、電文はキューに届いていた。
`gateway` が読んでいなかった。

原因は `read()` が**データが来るまで無期限にブロックする**こと。

ループ先頭 → キューを覗く（空）→ read() でブロック ← ここから戻らない

上り電文はブロック中に到着するため、**次の下り電文が来るまで永久に読まれない。**
下り電文が来なければ、キューに溜まり続ける。

**この問題は「gateway が常駐する」ことで悪化する。**
プロセスが短命なら1件失うだけだが、常駐すると滞留が蓄積し、
キューが満杯になった時点で上流（`termd`）の送信までブロックする。

### 選択肢

1. **`select()` でタイムアウト付きに読み、毎周期キューを覗く**
2. `select()` でストリームとキューを同時に待つ
3. 受信専用スレッドを分ける

### 決定

**案1。`select()` で最大 100ms 待ち、タイムアウトしたらループ先頭に戻る。**

キューを覗く → select(fd, 100ms) → データがあれば読む / 無ければ戻る

### 理由

- **案2は実現できない。System V メッセージキューはファイル記述子を持たない。**
  `select()` / `poll()` / `epoll()` はいずれも記述子を対象とするため、
  キューをストリームと同時に待つことができない。
  これは System V の設計上の制約であり、回避策は無い
- 案3はスレッドと同期機構を導入する。Step 3 の範囲を超える
- **一般則として、他の仕事も見る必要があるループの中では、
  無期限にブロックしうる呼び出しを置いてはならない。**
  実務のコードが受信にタイムアウトを指定しているのも同じ理由

### 代償

- **上り電文に最大 100ms の遅延が生じる。** 指令系の応答としては許容範囲
- **データが無くても 100ms ごとに起きる。** 完全なイベント駆動ではない
  → 実測して問題になるなら間隔を調整する。設定化は Step 7
- **`Process::run()` と `StreamProcess::run_stream()` で待ち方が違う。**
  前者はキューのタイムアウト、後者は `select` + キューのポーリング。
  この非対称性は System V の制約に由来し、解消できない
- **Step 6 で TCP に変えても、この構造は変わらない。**
  ソケットは記述子を持つが、キューは持たないため
  → **要検討**：POSIX メッセージキュー（`mq_open`）は記述子を返すため、
    案2が可能になる。ただし ARCHITECTURE §6 の記述と実務構成から離れる

## 検証方法

- **`gateway` を起動したまま下り電文を1件だけ流し、1秒以内に上りが表示されること。**
  表示されなければブロック問題が再発している
- **`gateway` を停止した状態で下りを流し、`termd` が
  `uplink dropped` を記録して継続すること。**
  停止・再送を試みるなら §3-6「上りは落としてよい」に反する
- 常駐状態で長時間動かし、`ipcs -q` の `messages` が増え続けないこと
