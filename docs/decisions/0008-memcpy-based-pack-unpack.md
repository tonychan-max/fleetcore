# 0008. pack/unpack は構造体を一括 memcpy し、多バイト項目のみ変換する

## 状態

採用 — 2026-08（Step 2 で実装）

## 背景

Step 2 でバイト列と構造体の相互変換を実装する。
ワイヤ上は big-endian、構造体はホストのバイトオーダ（ARCHITECTURE §4-3）。

**実装方式によって、ADR-0003 の `static_assert` が意味を持つかどうかが変わる。**

## 選択肢

1. **構造体を一括 `memcpy` し、多バイト項目だけ `offsetof` で上書き変換する**
2. フィールドごとに読み書きする（`h.length = load_be16(buf + 4)` のように）
3. バッファのポインタを構造体ポインタに `reinterpret_cast` する

## 決定

**案1。`memcpy` + フィールド単位のバイトオーダ変換。**

```cpp
std::memcpy(&out, buf, sizeof(Header));
out.length = load_be16(buf + offsetof(Header, length));
```

## 理由

- **案2を採ると ADR-0003 が無意味になる。**
  フィールドごとにオフセットを直接書くなら、構造体のレイアウトがワイヤと一致している
  必要が無い。`static_assert` は飾りになり、このプロジェクトの主題を自ら壊す
- **案1は「構造体レイアウト == ワイヤレイアウト」を前提とする。**
  つまり `static_assert` が飾りではなく**必需品**になる
- 実務で経験したオフセットずれの不具合は、まさに案1の構成で起きるもの。
  clean-room 再実装の意義は、同じ問題を再現した上で解決手段を示すことにある
- 固定長プロトコルでは案1の方が短く、速い

## 案3を採らない理由

```cpp
const Header* h = reinterpret_cast<const Header*>(buf);   // 採用しない
```

最も自然に見えるが、2つの問題がある。

1. **アラインメント。** `buf` の先頭アドレスが 8 の倍数とは限らない。
   未整列アドレスから `uint64_t`（`timestamp`）を読むのは未定義動作であり、
   アーキテクチャによってはハードウェア例外で落ちる
2. **strict aliasing。** `uint8_t*` を `Header*` として読むことは規格上許されない。
   コンパイラは「この2つは別物を指す」と仮定して最適化してよく、
   最適化レベルを上げた途端に挙動が変わりうる

**`memcpy` を通せば両方回避できる。** 現代のコンパイラはこの `memcpy` を最適化で消すため、
性能上の損失は無い。

この書き方が動いているのは、x86 が未整列アクセスを許容しているからである。
移植した瞬間に問題になる種類のコードであり、**動作実績は正しさの証明にならない。**

## 代償

- **構造体レイアウトへの依存が実装に入り込む。**
  `#pragma pack` が効かない処理系では黙って壊れる
  → ADR-0003 の `static_assert` がこれを検出する。**2つの ADR は対で成立している**
- `offsetof` を実装内に直接書くため、フィールド追加時に修正箇所が増える
  → Phase 3 の生成器がこの部分ごと生成する（ADR-0004）
- 内部 IPC 構造体（`IpcLockRequest`）には `#pragma pack` を付けていない。
  外に出ないため処理系間の一致が不要だからだが、**この非対称性は説明が要る**
  → 契約（外向き）と実装（内向き）の違いそのもの。ARCHITECTURE §3-1 の四層に対応する

## 検証方法

- **GCC / Clang / MSVC の3種でビルドし、`layout_dump` の出力が完全に一致することを確認する。**
  一致しなければ「レイアウト == ワイヤ」という前提が処理系依存だったということ
  （CI は Step 8 に延期。それまでは手動）
- `-fsanitize=alignment` を有効にして実行し、警告が出ないこと（**未実施**）
