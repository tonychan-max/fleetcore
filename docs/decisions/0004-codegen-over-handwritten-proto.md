# 0004. 電文定義をコード生成に置き換える

## 状態

**提案** — 2026-08（Phase 3 で着手予定。未実装）

## 背景

ADR-0003 で `static_assert` によるレイアウト検証を導入したが、代償が残っている。

- `static_assert` 自体を書き忘れると効果がゼロ
- 期待値（サイズ・オフセット）を人が計算して書く
- 送信側と受信側で構造体定義を二重に持つと、片方だけ直す事故が起きる
- 仕様書（人間向け）と `proto.h`（機械向け）が二重管理になる

**根本原因は、契約の記述が2箇所以上に存在すること。**

自動車業界は同じ問題を DBC ファイル + コード生成で解決している。
ECU が数百・サプライヤが数十社という規模では人力照合が破綻するため。
それを最小構成で再現する。

## 選択肢

1. **定義ファイル（YAML）から C++ を生成する**
2. IDL を使う（Protocol Buffers / FlatBuffers / Cap'n Proto）
3. Qt Remote Objects の `.rep` + `repc` を使う
4. 手書きを続け、レビューで担保する（現状）

## 決定

**自作の生成器（Python）：YAML → C++ 構造体 + `static_assert` + pack/unpack 関数。**

```yaml
protocol:
  name: mini-lock
  version: 1
  endian: big

messages:
  - name: LockRequest
    code: 0x10
    direction: down
    droppable: false
    since_version: 1
    fields:
      - { name: term_no, type: ascii, len: 4 }
```

## 理由

- **既製の IDL（案2）は、バイト列レイアウトを自分で決められない。**
  Protocol Buffers は可変長エンコードで、既存のバイナリ電文仕様に合わせられない。
  「既に決まっている固定長レイアウトに適合させる」という本来の問題を解かない
- **FlatBuffers は近いが、既存プロトコルへの後付けには重い。** 学習目的にも大きすぎる
- **`repc`（案3）は Qt 内のオブジェクト間通信が対象**で、対外バイナリ電文の生成器ではない
  → ただし **DSL 設計の参考として非常に価値がある**。自分の YAML を設計したあとに文法を読み、
    取りこぼした概念（権限の非対称性など）を確認する
- **自作する最大の理由は学習目的。** 生成器を書くこと自体がこのプロジェクトの中心

## 代償

- **生成器のバグは全電文に波及する。** 手書きなら1箇所の間違いが、生成器では全体の間違いになる
  → 対策：生成器自体に単体テストを持たせる。既知の入力に対する出力をゴールデンファイルで固定する
- ビルド手順が増える（生成 → コンパイル）。CI に組み込む必要がある
- 生成物を repo にコミットするか否かの判断が要る
  → **コミットする**。生成器が無い環境でもビルドでき、差分レビューで生成結果の変化が見える
- YAML の表現力が足りない場面が必ず来る（可変長、条件付きフィールド、配列）
  → 最初から全部やらない。**固定長のみ**で始め、必要になってから拡張する

## 検証方法

**Step 15：第二のプロトコルを同じ生成器で通す。**

```
tools/codegen/schema/
├── minilock.yaml      ← 自分のプロトコル
└── sample_can.yaml    ← 簡略 CAN フレーム群
```

同一の生成器・同一のコードパスで両方が処理できれば、
「この生成器は特定業界に依存していない」という主張が**検証済みの事実**になる。
通らなければ、抽象化が自分のプロトコルに寄りすぎていたということ。
