# 0013. gateway は標準入力ではなく TCP で保守端末を待ち受ける

## 状態

採用 — 2026-08（Step 6 で実装）

## 背景

Step 2〜3 の `gateway` は標準入力からバイト列を読んでいた。
`msggen | gateway` という形で骨格を通すための仮の入口である。

Step 6 で保守画面（`maint_gui`）を作るにあたり、本来の入口に置き換える。

## 選択肢

1. **`gateway` を TCP サーバにし、保守端末が接続する**
2. `gateway` が保守端末に接続しにいく
3. 標準入力のまま、`maint_gui` から名前付きパイプに流す

## 決定

**案1。`termd` と同じ `TcpServer` を使い、ポート 9100 で待ち受ける。**

`StreamProcess`（標準入力用の派生クラス）は不要になり、
`gateway` は他の業務プロセスと同じ `Process` を継承する形に戻った。

## 理由

- **待ち受ける側と接続しにいく側の役割は、可用性で決まる。**
  サーバは常駐し、端末は現れたり消えたりする。
  常にいる側が待ち、来る側が接続するのが自然
- **`termd` と同じ構造になる。** `TcpServer` と `StreamBuffer` を
  そのまま再利用でき、新しい概念が増えない
- 案3は `maint_gui` を作る意味を薄める。パイプ経由の入口は結局仮のまま

## 副次的な発見：`TcpServer` の置き場所

当初 `termd/tcp_server.cpp` に置いた。`termd` 専用のつもりだった。

`gateway` も必要になった時点で `common/` に移した。判断基準は
**「プロトコルを変えたとき、誰が変わるか」**。

- プロトコルが変わる → `wire.cpp` は書き直し
- プロトコルが変わる → `tcp_server.cpp` は**1行も変わらない**

つまり `TcpServer` は契約ではなく **OS の道具**であり、
ARCHITECTURE §3-1 の四層でいえば最下層に属する。`msgq` と同じ位置。

**最初から `common/` に置くべきだった。** 業務プロセスのディレクトリに
道具を置いたのは分類の誤りである。

## 代償

- **接続を1本しか保持しない。** 2台目の保守端末が接続すると、
  1台目のソケットは閉じられる
  → `termd` は端末ごとに1プロセスなので1対1で正しい（ARCHITECTURE §3-3）。
    しかし `gateway` は本来 N 台の保守端末を相手にしうる。
    **現状は制約であり、設計ではない**
  → 複数保持するなら、送信の直列化（§3-3 の「漏斗」）が必要になる。
    Phase 4 以降で扱う
- **ストリームが同期を失ったとき、接続を切る。**
  保守端末は再接続するが、その間に出された指令は失われる
  → 下りは落としてはいけない（§3-6）ため、本来は store-and-forward が要る。
    Phase 4 の課題
- **`gateway` も `termd` も、ソケットとキューの2入力を持つ。**
  System V キューは記述子を持たないため `select` で同時に待てず、
  `on_idle()` でのポーリングになる（ADR-0010）。
  ソケット側を非ブロッキングにすることで両立させているが、
  **完全なイベント駆動ではない**

## 保守端末側の構成

`maint_gui` は `term_gui` と同じ2スレッド構成（ADR-0012）を採る。
方向だけが逆になる。

| | term_gui | maint_gui |
|---|---|---|
| 送る | （なし） | LockRequest |
| 受ける | LockRequest | LockResponse |
| GUI → worker | （なし） | ボタン押下 → `sendLock` |

**`sendLock` はスロットとして定義した。** ボタン押下は GUI スレッドで起きるが、
ソケットは worker スレッドのものだからである。
シグナル/スロット経由にすることで、Qt が呼び出しを worker スレッドに投入し、
**ソケットに触れるのは常に worker スレッドだけ**という不変条件が保たれる。

`seq` の採番も worker が持つ。GUI 側に持たせると、
複数の入口から送信する将来の構成で重複しうる。

## 検証方法

- **保守端末が接続していない状態で上りが届いたとき、記録して継続すること。**
  再送や保持を試みるなら §3-6「上りは落としてよい」に反する
- **`gateway` を落として再起動したとき、`maint_gui` が自動で復帰すること**
- 2台目の保守端末を接続し、1台目が切られることを確認する。
  これが受け入れられない要件になった時点で、この ADR を見直す
