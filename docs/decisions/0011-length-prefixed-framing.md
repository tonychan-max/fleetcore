# 0011. TCP のフレーム境界はヘッダの `length` で復元する

## 状態

採用 — 2026-08（Step 6 で実装）

## 背景

Step 6 で TCP を導入した。ここで初めて「電文の境界」という問題が現れる。

メッセージキューには境界がある。`msgrcv` は1件を返し、2件が混ざることはない。
**TCP にはそれが無い。** 送信側の `send` と受信側の `recv` は1対1に対応しない。

1回の `recv` が返しうるもの：

- 電文の途中まで
- 電文1件ちょうど
- 電文1.5件
- 電文3件

**「1回の `recv` で受け取ったものが1電文」と仮定するのが、
メッセージキューから TCP へ移るときの最も一般的な誤りである。**

## 選択肢

1. **共通ヘッダの `length` を見て、その長さ分を1電文として切り出す**
2. 区切り文字（デリミタ）を入れる
3. 全電文を固定長にする
4. 送信のたびに接続を張り直す

早期に外したもの：

- **`recv` の戻り値をそのまま1電文とみなす** — 前述のとおり成立しない

## 決定

**案1。`common/stream_buffer.h` の `StreamBuffer` が担当する。**

```
append(受信したバイト列)
    ↓
next() → ヘッダ分（20バイト）あるか？
           ↓ ある
         length を読む
           ↓
         length バイト揃っているか？
           ↓ 揃っている
         その範囲を1電文として返す
    ↓
consume(len) で消費した分を捨てる
```

## 理由

- **`length` は既に契約に入っている。** ARCHITECTURE §4-1 で
  「未知電文の読み飛ばしに必須」として Phase 1 の時点で入れた項目であり、
  ここで second use が生まれた。**後から追加できない項目を先に入れておいた判断が回収された**
- **案2（デリミタ）はバイナリでは使えない。** 区切り文字と同じバイト値が
  データ中に現れる。エスケープ処理が必要になり、電文長が可変になり、
  固定長レイアウトを前提とする ADR-0003 と衝突する
- **案3（全電文固定長）は最大長に合わせた無駄が出る。**
  将来の可変長電文（自由文、ファイル転送）を最初から排除してしまう
- **案4（毎回接続）は接続確立のコストが電文送信のコストを上回る。**
  車載端は常時接続が前提

## 代償

- **受信側にバッファ管理の責任が生まれる。**
  `next()` が返すポインタは内部バッファを指しており、次の `append()` /
  `next()` までしか有効でない。この契約を守らないと解放済み領域を読む
  → 対策：`next()` は覗くだけ、`consume()` で明示的に捨てる、という2段構成にした。
    1つの関数で「返して捨てる」にすると、返したポインタが即座に無効になる
- **`length` が壊れた場合、どこから再同期すればよいか分からない。**
  バイト列の途中に「たまたま正しく見えるヘッダ」がある可能性もある
  → 対策：接続を切る。車載端・保守端とも自動再接続するため、
    両端が既知の状態に戻る。**マジック値を探して読み飛ばす方式は採らない**
    （誤った位置で同期して、壊れたデータを正常として処理する危険がある）
- バッファに `std::vector` を使っており、`consume()` のたびに先頭からの
  `erase` が発生する。電文サイズが小さいため問題にならないが、
  高頻度・大容量になればリングバッファが必要

## 検証方法

- **1回の送信を意図的に分割して送り、正しく組み立てられるか。**
  `nc` で1バイトずつ流すか、送信側に `sleep` を挟む
- **2電文を1回の `send` でまとめて送り、2件として処理されるか**
- `length` を壊した電文を送り、接続が切れて再接続されること。
  再接続後に正常な電文が処理できること
