# 0003. 電文構造体のレイアウトを `static_assert` で検証する

## 状態

採用 — 2026-08

> **このプロジェクトの主題にあたる判断。** README の中心もここ。

## 背景

バイナリプロトコルでは、送信側と受信側が**1バイトのズレも無く同じ解釈をする**必要がある。
しかし C/C++ の構造体レイアウトは、次の理由で書いた通りにならないことがある。

- コンパイラのパディング挿入
- フィールドの追加・削除・順序変更
- **共通ヘッダの記述漏れ**（構造体の先頭にヘッダを書き忘れると、以降の全フィールドがズレる）

そして重要なのは、**これらはすべてコンパイルを通る**ということ。
実行時に「なぜか値がおかしい」という形でしか現れず、
ログを追ってバイト位置を数えるまで原因が分からない。

実際に業務で、構造体のヘッダ定義が抜けていたために
読み取り位置が後続フィールド分ずれるという不具合を経験した。
**原因は、契約が人間向けの仕様書としてしか存在せず、機械が検証できなかったこと。**

## 選択肢

1. **`static_assert` でサイズとオフセットをコンパイル時に検証する**
2. 実行時に初期化処理でサイズを検証し、不一致ならログを出して停止する
3. 単体テストでサイズを検証する
4. レビューと仕様書で担保する（＝実務の現状）

## 決定

**`static_assert(sizeof(...))` と `static_assert(offsetof(...))` を全電文構造体に付ける。**

```cpp
#pragma pack(push, 1)
struct LockRequest {
    Header header;
    char   term_no[4];
};
#pragma pack(pop)

static_assert(sizeof(LockRequest)          == 24, "LockRequest 全体長");
static_assert(offsetof(LockRequest, term_no) == 20,
              "端末番号は共通ヘッダの直後から始まる");
```

`#pragma pack(1)` と併用する。**pack だけでは不十分**で、
pack はパディングを消すが、フィールドの記述漏れは検出しない。

## 理由

- **実行時コストがゼロ。** コンパイル時に消える
- **テストを書く必要が無い。** ビルドすれば必ず検証される。テストの実行忘れが原理的に起きない
- **失敗時のメッセージを日本語で書ける。** 何が壊れたかが即座に分かる
- 実行時検証（案2）は、**その行に到達しないと分からない**。組込み端末で現場に出てから分かるのでは遅い
- 単体テスト（案3）は、テストを書き忘れた構造体が守られない

## 代償

- **`static_assert` 自体を書き忘れると意味が無い。**
  → これが Phase 3（コード生成）に進む理由。**人が書く限り書き忘れる**ので、生成物にする（ADR-0004）
- 期待値（`== 24` 等）を**手で計算して書く**ことになる。ここを間違えると誤った値で固定してしまう
  → 対策：`common/layout_dump.cpp` で実際のサイズとオフセットを出力し、**実測値を見てから**期待値を書く。
    フィールドを足したときも同じ手順を踏む
- `#pragma pack` は厳密には処理系依存（GCC/Clang/MSVC はいずれも対応）

## 検証方法

**README に載せる実験がそのまま検証になる。**

`LockRequest` から `Header header;` を1行消して `make` する。

```
error: static assertion failed: 端末番号は共通ヘッダの直後から始まる
```

**業務で1日かけて追いかけた不具合が、1秒でコンパイルエラーになる。**
この差がこのプロジェクトを作った動機そのものであり、
スクリーンショットとして README の先頭に置く。
