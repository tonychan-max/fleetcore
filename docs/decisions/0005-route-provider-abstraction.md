# 0005. 外部の経路探索サービスを抽象化し、既定を Mock にする

## 状態

**提案** — 2026-08（Phase 6 で着手予定。未実装）

## 背景

Phase 6 で地図表示と経路案内を実装する。
経路探索には外部サービス（商用地図 API、OSRM 等）が必要になる。

外部サービスには、コードの品質と無関係な性質がある。

- 料金体系が変わる／有料化される／終了する
- 利用規約が変わる（表示方法・キャッシュ・併用の制約）
- API キーが必要で、**公開リポジトリに置けない**
- レート制限・障害・ネットワーク不通がある

**これらは必ず起きる。** 起きたときに壊れる範囲を、あらかじめ限定しておく必要がある。

## 選択肢

1. **インタフェースを切り、Mock を既定実装にする**
2. 商用 API を直接呼ぶ
3. OSRM を self-host して直接呼ぶ
4. 経路探索は実装しない（直線表示のみ）

## 決定

**`IRouteProvider` を定義し、既定実装を `MockRouteProvider` とする。**

```cpp
class IRouteProvider {
public:
    virtual ~IRouteProvider() = default;
    virtual Result<Route> route(Coord from, Coord to) = 0;
};
```

| 実装 | 用途 | 既定 |
|---|---|---|
| `MockRouteProvider` | 直線 + 固定速度。ネットワーク不要 | **○** |
| `OsrmRouteProvider` | 実地図。self-host または公開デモサーバ | |
| 商用 API Provider | 環境変数に鍵があるときのみ有効化 | |

**CI は `MockRouteProvider` だけを使う。**

## 理由

- **ネットワークと課金に依存するテストは CI を不安定にする。**
  外部サービスの障害でビルドが赤くなるのは、自分のコードの品質を反映していない
- **API キーを公開リポジトリに置けない。** 鍵が無いと動かない設計にすると、
  clone した他人が何も動かせない。作品として成立しない
- 規約変更・値上げ・終了が起きたとき、**壊れるのは1ファイルだけ**になる
- 抽象化の粒度は「経路を返す」という業務上の関心事に置く。
  外部サービス固有の概念（waypoint 形式、レスポンス JSON 構造）を上位に漏らさない

これは DDD で言う**腐敗防止層（anti-corruption layer）**にあたる。
長期保守されるシステムが保守できているのは、外部との境界が薄い1枚に閉じているため。

## 代償

- **抽象化のコストが先に発生する。** 実装が1つしか無い段階でインタフェースを切るのは、
  一般には早すぎる最適化と見なされうる
  → ただし外部サービスに限っては、**後から切るのは事実上不可能**。呼び出しがコード中に散った後では遅い
- **インタフェースが最初の実装に引きずられる。**
  `MockRouteProvider` の都合で設計すると、実サービスを繋いだときに合わなくなる
  → 対策：Mock を書く前に OSRM のレスポンス構造を読み、**実サービス側の制約からインタフェースを決める**
- Mock で開発していると、実サービス特有の問題（遅延、部分失敗、座標系の差）に気づくのが遅れる

## 検証方法

- `OsrmRouteProvider` を追加したときに、**`IRouteProvider` の定義を変更せずに済むか。**
  変更が必要なら抽象化が Mock に寄りすぎていた
- 鍵もネットワークも無い環境で `git clone` → ビルド → 起動 → 経路表示まで到達できるか

## 備考：商用地図 API について

技術的には REST + JSON で問題なく実装できる。
ただし**利用規約は着手時点のものを必ず自分で確認すること。**
表示方法・キャッシュ可否・他社地図との併用について制約があり、時期によって変わる。

このドキュメントの記述を根拠にしない。
