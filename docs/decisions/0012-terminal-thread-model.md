# 0012. 端末側は通信スレッドと GUI スレッドに分け、シグナルのみで繋ぐ

## 状態

採用 — 2026-08（Step 6 で実装）

## 背景

`term_gui` は2つのことを同時にする必要がある。

- TCP で `termd` から電文を受け取る
- 画面を描画し、操作に応答する

Qt のイベントループ（`app.exec()`）は1つのスレッドで1つ。
通信のためにブロックすると画面が固まり、画面の処理中は電文を取りこぼす。

## 選択肢

1. **通信専用スレッドを分け、シグナル/スロットで GUI に渡す**
2. `QTimer` で定期的にソケットをポーリングする
3. `QSocketNotifier` でソケットをイベントループに載せる

## 決定

**案1。`CommWorker` を `QThread` に `moveToThread` し、
`emit lockReceived(req)` で `LockWindow` のスロットを呼ぶ。**

```
worker スレッド                    GUI スレッド
──────────────                    ────────────
QTcpSocket
  readyRead
    → unpack
    → emit lockReceived  ─────→  イベントキュー
                                    → onLockReceived
                                        → 画面更新
```

## 理由

- **案1が Qt における標準構成である。** 特別な工夫ではなく、
  この形を知らないことの方が問題になる
- **シグナル/スロットはスレッドを跨ぐときにキュー経由になる。**
  送信側と受信側が別スレッドだと、Qt は直接呼ばずに
  引数を複製して受信側のイベントキューに投入する。
  **これはサーバ側プロセス間のメッセージキューと同じ原理**であり、
  「相手のループに出来事を渡す。相手の内部に手を伸ばさない」という
  同一の原則が1段下のレイヤで再び現れている。
  **結果として、このプログラムには mutex が1つも無い**
- **案2（`QTimer` ポーリング）は動くが、遅延を自分で作ることになる。**
  ソケットは記述子を持つのだから、待てるものを待たずにポーリングする理由が無い
- **案3（`QSocketNotifier`）は単一スレッドのまま動くが、
  受信処理が重くなると画面が固まる。**
  `unpack` は軽いが、Phase 6 で地図データを扱う段階では成立しなくなる

## スレッド境界は将来のプロセス境界

ADR-0001 で、Phase 2 に端末内部を複数プロセスに分割することを決めている。
`CommWorker` / `LockWindow` の境界は、**その分割線と一致するように引いた。**

- `LockWindow` はソケットもキューも知らない。
  復号済みの `LockRequest` を渡されて表示するだけ
- 実際 Step B-1 ではテスト用ボタンから、B-3 では worker から同じスロットを呼んでいる。
  **供給元が変わっても `LockWindow` は1行も変わらなかった**
- Phase 2 で worker が別プロセスになり QLocalSocket 経由になっても、同じことが言える

## 代償

- **`QObject` はスレッドに属する、という規則を守る必要がある。**
  `QTcpSocket` は `moveToThread` の**後**、`start()` の中で生成しなければならない。
  コンストラクタで生成すると GUI スレッドに属し、`readyRead` が
  GUI スレッドで配送され、そのスロットが worker のデータを触る。
  **コンパイルも実行も通り、たまにデータが壊れる**という最悪の壊れ方をする
- **スレッドを跨ぐシグナルは引数の型登録が要る。**
  `Q_DECLARE_METATYPE` と `qRegisterMetaType` の両方。
  無いと Qt は警告を1行出して**黙って何もしない**
- **`Q_DECLARE_METATYPE` はテンプレート特殊化であり、
  プログラム全体で1箇所にしか書けない。**
  最初は各ヘッダに書いたが、2つ目のヘッダが同じ型を必要とした時点で
  インクルード順に依存する壊れ方をした
  → `common/qt_metatypes.h` に集約した。
  **契約は1箇所、という ADR-0003 と同じ原則がここでも要る**
- 終了時にスレッドを明示的に止める必要がある（`quit()` + `wait()`）。
  怠ると Qt が警告を出し、場合によっては落ちる
- **`emit` の直後にスロットが実行済みだと仮定できない。**
  C# の `event` は同期呼び出しなので、この点は移行時に誤りやすい

## 検証方法

- **画面を長時間開いたまま電文を流し、取りこぼしが無いこと。**
  取りこぼすなら worker がイベントループを離れている
- **`termd` を落とし、2秒後に再接続すること。**
  再接続がループではなく `QTimer::singleShot` で実装されているのは、
  スレッドがイベントループに留まる必要があるため
- **Phase 2 でプロセス分割したとき、`LockWindow` を変更せずに済むか。**
  変更が必要なら、境界の引き方が間違っていた
