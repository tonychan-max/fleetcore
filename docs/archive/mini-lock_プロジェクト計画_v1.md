# mini-lock 移植プロジェクト　全体計画

> **目的**：実務で担当している Windows ベースの多プロセス指令システムと同じアーキテクチャを、Linux + Qt6 + モダン C++ で再設計・再実装する。
> **性質**：**clean-room 重写**。アーキテクチャ思想（通用工程模式）のみ流用し、会社のコード・電文番号・構造体・プロセス命名は一切持ち込まない。GitHub に公開できる成果物とする。
> **README で会社名・システム名・顧客名・電文番号は書かない。**「実務で類似システムを担当」まで。

---

## 0. 全体アーキテクチャ

```
maint_gui (Qt6)          保守画面：端末を選んでロックボタン
    │ TCP
    ▼
gateway   (1000)         対外窓口。電文を解析して内部メッセージへ
    │ msgq
    ▼
locator   (2000)         端末番号 → 端末索引を解決（共有メモリ参照）
    │ msgq
    ▼
termd     (3000+n)       端末ごとに1プロセス。TCP で端末へ
    │ TCP
    ▼
term_gui  (Qt6)          車載画面：ロック表示・解除認証
```

**プロセス索引にID を埋め込む**（`3000 + 端末番号`）ことで、`termd` だけが複数プロセス並存できる。これは実務システムの最も美しい設計なので必ず再現する。

## 1. 設計原則（討論から抽出したもの）

プロジェクト全体を貫く判断基準。迷ったらここに戻る。

### 1-1. 四層フレーム

| 層 | 内容 | 性質 |
|---|---|---|
| **電文の流れ** | バイト列の契約 | **契約**（両端で1バイトも違えない） |
| **業務駆動** | 解析 → 解決 → 変換 | 実装 |
| **フレームワーク** | プロセス構成・IPC の使い分け | 実装 |
| **言語/OSの道具** | 共有メモリ・セマフォ・スレッド | 実装 |

**契約は1つだけ**（`common/proto.h`、Phase 3 以降は生成物）。他はすべて各プロセスの自由。

### 1-2. 業務駆動は三動作の組み合わせ

どの電文も結局これしかやっていない。

| 動作 | mini-lock での担当 |
|---|---|
| **解析** | `gateway`：バイト列 → 構造体 |
| **解決** | `locator`：端末番号 → 端末索引 |
| **変換** | `termd`：内部形式 → 端末向け形式 |

### 1-3. 多対一なら漏斗、一対一なら不要

**ソケットに書き手が複数いるかどうか**で設計が決まる。

- `gateway` ← maint_gui は多対一になりうる → **送信キュー + 送信スレッドで直列化**
- `termd` → 端末は一対一（プロセスが端末ごと）→ **直接送信でよい**

TCP はバイトストリームなので、複数スレッドが同時に書くと電文が混ざる。キューはその直列化装置。

### 1-4. snapshot と delta を分ける

- **共有メモリ = snapshot**（今の状態、非破壊読み取り、何度でも読める）
- **メッセージ = delta**（起きた事、破壊的読み取り、1人だけが受け取る）

状態を変えたら「変えた」を別途通知する。共有メモリは通知機能を持たない。

### 1-5. claim-check（データは預け、キーだけ渡す）

同一マシン内はデータを共有領域に置いてキーだけ流す。跨マシンは全部送るしかない。
大きいファイルは別経路（実務では FTP）。

### 1-6. 落としていいもの・落としてはいけないもの

- **上り（状態通知）は落としてよい**：新しい値が来れば古い値に意味はない
- **下り（指令）は落としてはいけない**：store-and-forward + retry で必ず届ける

## 2. ロードマップ

### Phase 1　骨格（CLI → GUI）

| Step | 内容 | 実務での対応 |
|---|---|---|
| 1 | プロトコル定義 + `static_assert` + CMake | 電文構造体定義 |
| 2 | CLI で骨幹貫通（gateway → locator → termd） | 3プロセス転送チェーン |
| 3 | 共有メモリ + セマフォ（端末テーブル） | 車両情報テーブル + 排他 |
| 4 | SQLite 認証（**パスワードはハッシュ保存**） | Access mdb + 平文比較 |
| 5 | `term_gui`（Qt6 ロック画面 + 解除認証） | 車載ロック画面 |
| 6 | `maint_gui`（Qt6 保守画面） | 保守画面 |
| 7 | signal / systemd（優雅終了・常駐・ログ） | プロセス監視 + 起動バッチ |
| 8 | gtest + GitHub Actions CI | （実務には無い） |

### Phase 2　端末内部の多プロセス化

実務の車載端（全体制御 + ミドル連携 + 各画面）に相当する部分。

| Step | 内容 |
|---|---|
| 9 | `term_router`（中央交換機）+ 転送表ファイル |
| 10 | `term_gui` を recv / router / ui の3プロセスに分割、**QLocalSocket** で接続 |
| 11 | `QSharedMemory` + 変更通知（snapshot / delta の分業を実装で確認） |

**QLocalSocket を選ぶ理由**：Linux では Unix domain socket、Windows では named pipe に自動で切り替わる。**同じコードが両OSで動く**。依存ゼロ（Qt のみ）。D-Bus は dbus-daemon 常駐が前提になるため、組込み向けには重い。

### Phase 3　契約の自動化（CAN / DBC 方式の模倣）★新規

**このプロジェクトで最も語れる部分。**

実務で踏んだ「構造体にヘッダ定義が抜けていて、車番の読み取り位置が8バイトずれた」バグ。原因は**契約が人間向けの仕様書しかなく、機械が検証できなかった**こと。

自動車業界は同じ問題を DBC ファイル + コード生成で解決している（ECU が数百・サプライヤが数十社では人力照合が破綻するため）。それを最小構成で再現する。

| Step | 内容 |
|---|---|
| 12 | 電文定義ファイル（YAML）を設計する |
| 13 | 生成ツール（Python）：YAML → C++ 構造体 + `static_assert` + 組み立て/解析関数 |
| 14 | `proto.h` を生成物に置き換え、手書き定義を廃止 |

**定義ファイルのイメージ**

```yaml
messages:
  - name: LockRequest
    code: 0x10
    direction: down
    fields:
      - { name: term_no, type: ascii, len: 4 }
```

**生成される C++**

```cpp
struct LockRequest {
    Header header;
    char   term_no[4];
};
static_assert(offsetof(LockRequest, term_no) == 16, "自動生成：位置検証");
static_assert(sizeof(LockRequest) == 20, "自動生成：サイズ検証");
```

**効果**：実務で1日かけて追いかけたバグが、**定義ファイルを直せば両端が同時に直る**構造になる。手で構造体を書く余地が消える。

### Phase 4（任意）　上り方向の追加

下り（ロック指令）だけでなく、上り（ロック完了通知 / 状態通知）を追加する。

- 入口と出口が入れ替わるだけで、形は同じ（`対外窓口 → 業務プロセス → 対外窓口`）
- **上りと下りで落とす方針が逆になる**（1-6）ことを実装で示せる
- `termd` に store-and-forward（端末オフライン時の保持と再送）を実装

## 3. Step 1 の要点（着手時の参照用）

```
mini-lock/
├── CMakeLists.txt
├── common/
│   ├── proto.h            ← 唯一の契約
│   └── layout_dump.cpp    ← レイアウト確認用
└── build/
```

**必ずやる実験**：`LockRequest` から `Header header;` を消して `make` する。

```
error: static assertion failed: 端末番号は共通ヘッダの直後から始まる
```

**実務で1日かかったバグが、1秒でコンパイルエラーになる。** これがプロジェクト全体の題眼であり、README に載せるスクリーンショット。

### 現代 C++ の書き方（実務との対比）

| 実務 | mini-lock | 差 |
|---|---|---|
| `#define D_CODE 0x69` | `constexpr uint8_t CODE_LOCK = 0x10;` | 型・スコープあり、**全角空格が混入したらコンパイルエラー** |
| `UCHAR` / `ULLONG` | `uint8_t` / `uint64_t` | ビット幅が名前にある、全プラットフォーム共通 |
| （対応物なし） | `static_assert` | コンパイル時検証、実行時コストゼロ |
| `char[]` で padding 回避 | `#pragma pack(1)` + `static_assert` | 明示 + 検証 |
