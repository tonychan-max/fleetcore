# 0002. 解除認証の資格情報は SQLite にハッシュで保存する

## 状態

採用 — 2026-08

## 背景

Phase 1 Step 4〜5。端末のロック解除には認証が要る。
資格情報の保存先と保存形式を決める。

前提：端末は物理的に持ち出される可能性がある。
**ストレージが第三者の手に渡る前提で設計する。**

## 選択肢

保存先：

1. **SQLite**
2. 平文の設定ファイル
3. 自前のバイナリファイル

保存形式：

1. **パスワードハッシュ（salt 付き、パスワード用 KDF）**
2. 平文
3. 可逆暗号化

## 決定

**SQLite + salt 付きパスワードハッシュ。**

ハッシュ関数は Argon2id を第一候補とし、依存を増やせない場合は bcrypt / scrypt。
**SHA-256 等の汎用ハッシュを単体では使わない**（高速すぎて総当たりに弱い）。

## 理由

- **平文保存は端末持ち出し時にそのまま漏れる。** 可逆暗号化も、復号鍵が同じ端末上にある以上ほぼ同じこと
- SQLite は単一ファイル・サーバ不要・パブリックドメイン相当。組込みでの実績が厚い
- 自前バイナリは、インデックスもトランザクションも自分で書くことになる。得るものが無い
- **比較はハッシュ同士で行う。** 平文パスワードをメモリ上に長く保持しない

## 代償

- **KDF の依存が増える。** libsodium もしくは Argon2 リファレンス実装が必要
  → 依存を避けるなら bcrypt の小規模実装。ただし**自作は絶対にしない**
- **検証コストが上がる。** Argon2 は意図的に遅い。組込み端末では体感遅延になりうる
  → パラメータ（メモリ・反復回数）を設定可能にし、`docs/CONFIG.md` に登録する
- パスワードを忘れた場合の復旧手段が無い（ハッシュなので原理的に不可）
  → 保守端末側からのリセット経路を設ける（Phase 4 以降）

## 検証方法

- DB ファイルを直接開いて、パスワードが読めないことを確認する
- 同じパスワードを2ユーザで登録し、**ハッシュ値が異なる**ことを確認する（salt が効いている証拠）

## 備考

実務の類似システムは Access mdb + 平文比較という構成だった。
**これは当時の制約下での判断であり、ここでの選択はそれへの批判ではない。**
ただし新規に作るなら平文を選ぶ理由は無い。この差分自体が学習項目。
