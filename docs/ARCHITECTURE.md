---

## 1. これは何か

多プロセス構成の端末ロック指令システム。
保守端末からロック指令を出し、複数の車載端末に配信し、端末側でロック画面を表示・解除認証する。

**性質**：業務で扱っている類似システムのアーキテクチャ思想のみを流用した clean-room 再実装。
既存コード・電文番号・構造体・プロセス命名は一切持ち込んでいない。

**目的**：Linux / モダン C++ / Qt6 の習得と、分散システム設計の実証。

## 2. 全体構成

```
maint_gui (Qt6)          保守画面：端末を選んでロックボタン
    │ TCP
    ▼
gateway   (1000)         対外窓口。電文を解析して内部メッセージへ
    │ msgq
    ▼
locator   (2000)         端末番号 → 端末索引を解決（共有メモリ参照）
    │ msgq
    ▼
termd     (3000+n)       端末ごとに1プロセス。TCP で端末へ
    │ TCP
    ▼
term_gui  (Qt6)          車載画面：ロック表示・解除認証
```

### プロセス一覧

| プロセス | 索引 | 役割 | 多重度 | Phase |
|---|---|---|---|---|
| `maint_gui` | — | 保守画面（Qt6） | 1 | 1 |
| `gateway` | 1000 | 対外窓口。バイト列 ⇄ 内部メッセージ | 1 | 1 |
| `locator` | 2000 | 端末番号 → 端末索引の解決 | 1 | 1 |
| `termd` | 3000+n | 端末1台に1プロセス。TCP 保持 | N | 1 |
| `term_gui` | — | 車載画面（Qt6） | 1/端末 | 1 |
| `term_router` | — | 端末内部の中央交換機 | 1/端末 | 2 |
| `term_sim` | — | ヘッドレス端末シミュレータ | 1（N台模擬） | 5 |
| `route_svc` | — | 経路探索の抽象窓口 | 1 | 6 |

### プロセス索引に ID を埋め込む

`termd` の索引は `3000 + 端末番号`。
これにより **`termd` だけが端末数だけ並存できる**。索引を見れば担当端末が分かり、
プロセス管理・ログ・監視のすべてが端末単位で自然に分離する。

## 3. 設計原則

判断に迷ったらここに戻る。詳細は計画書 §2。

### 3-1. 四層フレーム

| 層 | 内容 | 性質 |
|---|---|---|
| 電文の流れ | バイト列の契約 | **契約**（両端で1バイトも違えない） |
| 業務駆動 | 解析 → 解決 → 変換 | 実装 |
| フレームワーク | プロセス構成・IPC の使い分け | 実装 |
| 言語 / OS の道具 | 共有メモリ・セマフォ・スレッド | 実装 |

**契約は1つだけ**（`common/proto.h`、Phase 3 以降は生成物）。
他はすべて各プロセスの自由。

### 3-2. 業務駆動は三動作の組み合わせ

| 動作 | 担当 |
|---|---|
| 解析 | `gateway`：バイト列 → 構造体 |
| 解決 | `locator`：端末番号 → 端末索引 |
| 変換 | `termd`：内部形式 → 端末向け形式 |

### 3-3. 多対一なら漏斗、一対一なら不要

ソケットに**書き手が複数いるか**で設計が決まる。

- `gateway` ← 保守端末は多対一になりうる → 送信キュー + 送信スレッドで直列化
- `termd` → 端末は一対一（プロセスが端末ごと）→ 直接送信でよい

TCP はバイトストリームなので、複数スレッドが同時に書くと電文が混ざる。

### 3-4. snapshot と delta を分ける

| | 実体 | 読み取り | 意味 |
|---|---|---|---|
| snapshot | 共有メモリ | 非破壊・何度でも | **今の状態** |
| delta | メッセージキュー | 破壊的・1人だけ | **起きた事** |

共有メモリは通知機能を持たない。状態を変えたら「変えた」を別途通知する。

### 3-5. claim-check

同一マシン内はデータを共有領域に置き、キーだけをメッセージで流す。
跨マシンは全部送るしかない。大容量ファイルは別経路。

### 3-6. 落としていいもの・いけないもの

- **上り（状態通知）は落としてよい**：新しい値が来れば古い値に意味は無い
- **下り（指令）は落としてはいけない**：store-and-forward + retry

この方針は電文定義そのものに `droppable` として持たせる（ADR-0006）。

### 3-7. 外部依存はインタフェース越しに置く

外部サービス名がコードの奥に現れてはいけない。既定実装は常に Mock。
詳細は ADR-0005。

### 3-8. 設定項目は台帳で一元管理する

`docs/CONFIG.md` が唯一の台帳。**「反映条件」列は空欄禁止**。

### 3-9. エラーの影響範囲を型で表す

**「エラーが起きたか」ではなく「どこまで壊れたか」で分類する。**

| Severity | 意味 | 制御 |
|---|---|---|
| `Message` | この電文だけが不正。次の電文へ | `continue` |
| `Stream` | バイト列が同期を失った。以降解析不能 | `break` |
| `Peer` | 特定の端末が不達。他端末は継続 | 記録して継続 |
| `Process` | 継続不能。終了して supervisor に委ねる | `return 1` |

等級はログにも出力する。`continue` か `break` かというコードの形からではなく、
**名前から回復戦略が読める**ようにするため。

詳細は ADR-0009。

## 4. 契約（プロトコル）

### 4-1. 共通ヘッダ

```cpp
#pragma pack(push, 1)
struct Header {
    uint8_t  magic[2];   // 'F','C' — 同期・誤接続検出
    uint8_t  version;    // プロトコル版数
    uint8_t  code;       // 電文種別
    uint16_t length;     // ヘッダ含む全長。未知電文の読み飛ばしに必須
    uint16_t seq;        // 連番。再送・重複検出
    uint64_t timestamp;  // 発生時刻（ミリ秒）
    uint32_t reserved;   // 将来用（0固定）
};
#pragma pack(pop)

static_assert(sizeof(Header) == 20, "共通ヘッダのサイズ");
static_assert(offsetof(Header, length) == 4, "length の位置");
```

**`version` と `length` は Phase 1 の時点で必ず入れる。**
後から入れることは事実上不可能で、無いと「電文を1つ足すために全端末同時更新」になる。

### 4-2. メッセージコード空間

**区画だけ先に決める。中身は空でよい。**

| 範囲 | 用途 | 方向 | 落としてよいか | Phase |
|---|---|---|---|---|
| `0x01`–`0x0F` | 接続管理 | 双方向 | × | 1 |
| `0x10`–`0x1F` | 制御指令（ロック・解除） | 下り | **×** | 1 |
| `0x20`–`0x2F` | 状態通知 | 上り | ○ | 4 |
| `0x30`–`0x3F` | 位置・移動情報 | 上り | ○ | 5 |
| `0x40`–`0x4F` | ナビゲーション | 双方向 | × | 6 |
| `0x50`–`0x5F` | ファイル転送（claim-check） | 双方向 | × | 任意 |
| `0xF0`–`0xFF` | 試験・異常注入 | 双方向 | ○ | 5 |

### 4-3. エンディアン

**ワイヤ上は big-endian（ネットワークバイトオーダ）で統一する。**

構造体はホストのバイトオーダで値を持つ。変換は `pack()` / `unpack()` の中だけで行い、
それ以外の場所にバイトオーダの知識を漏らさない。
（Phase 3 以降はこの変換も生成物が担保する）。

## 5. 端末テーブル（共有メモリ）

`locator` が参照し、`gateway` / `termd` が更新する snapshot。

```cpp
struct TermEntry {
    uint32_t term_no;       // 端末番号（0 = 未使用）
    uint32_t capabilities;  // 端末が接続時に申告する機能ビット
    uint8_t  state;         // 接続状態
    uint64_t last_seen;     // 最終受信時刻
};
```

### capability ビット

```cpp
constexpr uint32_t CAP_LOCK       = 1u << 0;
constexpr uint32_t CAP_POSITION   = 1u << 1;  // Phase 5
constexpr uint32_t CAP_NAVIGATION = 1u << 2;  // Phase 6
```

**capability は端末側が接続時に申告する。サーバの設定ファイルに持たせない。**
設定と実態がズレる事故が構造的に起きないため。新旧端末の混在がこれで成立する。

排他はセマフォ。読み取りは非破壊なので複数プロセスが同時に読んでよい。

## 6. IPC の使い分け

| 経路 | 方式 | 理由 |
|---|---|---|
| 保守端末 ⇄ `gateway` | TCP | 跨マシン想定 |
| `gateway` → `locator` → `termd` | System V メッセージキュー | delta の伝達。1人だけが受け取る |
| 端末テーブル | System V 共有メモリ + セマフォ | snapshot。何度でも読める |
| `termd` ⇄ 端末 | TCP | 跨マシン |
| 端末内部プロセス間（Phase 2） | **QLocalSocket** | ADR-0001 |
| 端末内部の状態共有（Phase 2） | `QSharedMemory` + 変更通知 | snapshot / delta の分業を Qt 側でも実演 |
